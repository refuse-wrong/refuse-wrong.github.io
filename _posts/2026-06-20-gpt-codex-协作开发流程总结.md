## 一、适用场景

这套流程适用于以下项目：

- 从零开始的新项目；
- 已有代码仓库，需要持续迭代；
- AI、数据、模型、自动化工具类项目；
- 需求复杂、无法一次性实现的工程；
- 希望由 GPT 负责规划与评审，Codex 负责代码实施的项目。

这套方法的核心不是让 AI 一次性“生成完整项目”，而是建立一个稳定的迭代闭环：

```text
GPT 规划
→ Codex 实施
→ GPT 复查
→ 用户确认
→ 进入下一阶段
```

---

## 二、三方角色分工

### 1. 用户：产品负责人和最终决策者

用户主要负责：

- 明确项目最终要解决的问题；
- 确定目标用户和使用场景；
- 明确哪些需求优先；
- 决定哪些限制不能突破；
- 对技术路线做最终选择；
- 判断阶段成果是否符合预期。

用户不需要在最开始就想清楚所有技术细节，但需要明确产品方向。

### 2. GPT：架构师、规划者、评审者和项目经理

GPT主要负责：

- 理解业务目标；
- 阅读和分析仓库；
- 发现当前设计中的问题；
- 设计系统架构；
- 拆分开发阶段；
- 定义每个阶段的验收标准；
- 编写可直接交给 Codex 的任务提示词；
- 复查 Codex 的代码提交；
- 判断当前阶段是否真正完成；
- 规划下一阶段；
- 维护整体路线，避免项目跑偏。

### 3. Codex：代码实施者

Codex主要负责：

- 按任务修改代码；
- 新增和重构模块；
- 编写测试；
- 执行测试；
- 更新 README 和使用文档；
- 输出修改摘要；
- 处理明确的工程问题。

Codex 更适合在清晰边界内执行任务，不适合独立决定整个产品路线。

---

## 三、标准协作闭环

推荐使用以下流程：

```text
1. 用户提出项目目标
2. GPT 理解目标与边界
3. GPT 阅读仓库
4. GPT 分析当前实现和根本问题
5. GPT 设计总体架构
6. GPT 拆分阶段路线
7. GPT 编写当前阶段 Codex 任务
8. Codex 修改代码并提交
9. GPT 读取最新 Commit
10. GPT 对照验收标准复查
11. GPT 指出问题和风险
12. GPT 更新项目阶段
13. GPT 编写下一阶段 Codex 任务
14. 重复以上流程
```

不要一次性要求 Codex 完成整个项目。

推荐每次只完成一个小阶段：

```text
一个清晰目标
+ 一组相关文件
+ 一组测试
+ 一个可运行入口
+ 一个可直观看到的结果
```

## 四、新项目最开始怎样向 GPT 发提示词

第一次提示词决定了 GPT 是直接写代码，还是先正确地规划项目。

不要只写：

```text
帮我做一个 XX 项目。
```

推荐使用以下模板。

### 新项目启动提示词模板

```text
我准备启动一个新项目：【项目名称】。

产品目标：
【说明最终解决的问题】

目标用户：
【说明谁会使用】

核心场景：
1. 【场景1】
2. 【场景2】
3. 【场景3】

当前资源：
- 仓库：【URL】
- 技术栈：【技术栈】
- 已有代码：【已有内容】
- 当前问题：【问题】

明确约束：
- 【约束1】
- 【约束2】
- 【约束3】

数据策略：
【真实数据 / 模拟数据 / 混合数据】

最终希望实现：
1. 【功能1】
2. 【功能2】
3. 【功能3】

请你先作为项目架构师，不要直接修改代码。

请完成：
1. 阅读并理解项目目标；
2. 如果有仓库，先展示默认分支最新 Commit；
3. 分析当前实现；
4. 找出缺失模块和潜在风险；
5. 设计整体系统架构；
6. 设计业务闭环、评估闭环、数据闭环和模型闭环；
7. 给出分阶段 Roadmap；
8. 为每个阶段定义输入、输出、测试和验收标准；
9. 明确哪些内容当前不做；
10. 给出第一阶段可直接交给 Codex 的详细任务提示词；
11. 每个阶段都规划一个可直观看到成果的输出，例如 CLI、Markdown 或 HTML 报告。
```

## 五、已有仓库时怎样让 GPT 阅读代码

推荐使用：

```text
这是我的仓库：
【仓库地址】

请先读取默认分支最新状态。

开始评估前，请先展示：
- 分支名；
- 最新 Commit SHA；
- Commit message；
- 与上次确认 Commit 的差异。

我要先确认你读取的是最新代码。

确认后请：
1. 阅读仓库目录；
2. 找出核心入口；
3. 阅读状态、数据、业务逻辑、模型、训练和测试；
4. 总结目前已经完成的能力；
5. 找出设计问题和缺失功能；
6. 区分基础设施问题和模型问题；
7. 给出分阶段完善计划；
8. 不要直接修改代码。
```

### 为什么必须先确认 Commit

GitHub 搜索索引可能滞后，因此正确顺序应是：

```text
读取默认分支 HEAD
→ 展示最新 Commit
→ 与上次 Commit 做 compare
→ 再阅读本次变更文件
```

以后每次都可以要求：

```text
后续每次读取仓库时，请先展示最新 Commit，并和上次确认的 Commit 比较。
```

## 六、GPT 的总体规划应包含什么

### 1. 当前真实状态

必须区分：

```text
项目当前实际具备什么
```

和：

```text
用户希望最终实现什么
```

例如：

```text
当前只是规则实验环境，还不是完整推荐助手。
```

### 2. 根本问题

GPT 应找出根因，而不是给出表面建议。

常见根因包括：

- 状态信息缺失；
- 动作空间不完整；
- 数据质量不足；
- 没有固定评估集；
- 训练与推理特征不一致；
- 奖励函数设计错误；
- 模型能力不足；
- 缺少产品入口；
- 缺少失败分析。

### 3. 目标架构

例如：

```text
输入
→ 状态解析
→ 合法动作生成
→ 规则评分
→ 推荐排序
→ 推荐解释
→ 固定评估
→ 数据生成
→ 模型训练
→ 产品入口
```

### 4. 阶段路线

推荐拆成：

```text
P0：基础业务闭环
P1：评估和数据闭环
P2：模型闭环
P3：多步决策
P4：产品化
```

### 5. 验收标准

每个阶段必须说明：

- 运行什么命令；
- 生成什么文件；
- 输出哪些指标；
- 哪些测试必须通过；
- 哪些内容不属于本阶段。

## 七、怎样给 Codex 编写任务提示词

Codex 提示词需要明确到文件、类、函数、测试和边界。

### Codex 任务标准结构

```text
# 任务名称

## 一、项目背景
说明为什么要做。

## 二、当前已完成
避免重复开发。

## 三、本次目标
只描述当前阶段。

## 四、具体任务
明确文件、类、函数、参数和行为。

## 五、测试要求
明确正常流程和边界情况。

## 六、验收命令
例如 python -m pytest -q。

## 七、不可做事项
限制任务范围。

## 八、兼容要求
说明不能破坏哪些接口。

## 九、完成后输出
要求 Codex 汇总文件、测试和限制。
```

### 通用 Codex 提示词模板

```text
请完成【阶段名称】。

当前项目已经完成：
- 【已有能力一】
- 【已有能力二】
- 【已有能力三】

本次目标：
【一句话说明目标】

具体任务：

1. 新增/修改文件
   - path/to/file.py
   - path/to/test.py

2. 实现接口
   class Xxx:
       def xxx(...):
           ...

3. 行为要求
   - 【规则一】
   - 【规则二】
   - 【边界情况】

4. 测试要求
   - 【测试一】
   - 【测试二】
   - 【测试三】

5. 更新文档
   - README.md
   - docs/usage.md

严格限制：
- 不要删除【旧模块】；
- 不要引入【复杂依赖】；
- 不要修改【非本阶段内容】；
- 不要破坏现有 CLI；
- 不要依赖网络；
- 保持旧测试通过。

验收标准：
python -m pytest -q

完成后请输出：
1. 修改文件列表；
2. 主要实现说明；
3. 测试结果；
4. 当前限制；
5. 下一阶段建议。
```

## 八、为什么每次只做一个阶段

一次性把整个规划交给 Codex 容易出现：

- 大范围重构；
- 破坏旧接口；
- 任务边界失控；
- 测试失败难以定位；
- Codex 自行猜测需求；
- 单次提交过大；
- GPT 难以完整复查；
- 表面功能齐全但内部逻辑不可靠。

推荐每个阶段控制在：

```text
1 个明确目标
3～8 个主要文件
1 组测试
1 个可执行命令
1 个成果展示入口
```

## 九、代码更新后怎样让 GPT 复查

推荐固定使用下面的提示词：

```text
代码已经更新，请你评估。

请严格按以下流程：
1. 直接读取默认分支 HEAD；
2. 展示最新 Commit SHA 和 message；
3. 与上次确认的 Commit 做 compare；
4. 阅读本次新增和修改的关键文件；
5. 对照上一阶段验收标准判断完成情况；
6. 检查实现质量、兼容性、测试和边界情况；
7. 指出明确问题和潜在风险；
8. 更新项目当前阶段；
9. 给出下一阶段规划；
10. 输出可直接交给 Codex 的下一阶段任务；
11. 说明我可以通过什么命令或报告直观看到这次更新的效果。
```

GPT 复查时应输出：

```text
最新 Commit
本次变更内容
阶段完成情况
实现优点
发现的问题
当前项目阶段
下一阶段目标
下一阶段 Codex 提示词
效果查看方式
```

## 十、怎样防止 GPT 和 Codex 跑偏

### 1. 保留项目总文档

建议仓库中建立：

```text
docs/
├── 00_PROJECT_VISION.md
├── 01_REQUIREMENTS.md
├── 02_ARCHITECTURE.md
├── 03_ROADMAP.md
├── 04_CURRENT_STATUS.md
├── 05_DATA_STRATEGY.md
├── 06_EVALUATION_PLAN.md
├── 07_USAGE.md
├── decisions/
└── tasks/
```

### 2. 每次声明当前阶段

例如：

```text
当前处于 P2.4。
本次只完成 P2.4。
不要提前做 P2.5。
```

### 3. 明确非目标

例如：

```text
本阶段不做：
- 强化学习；
- 多玩家大厅；
- 图像识别；
- 自动鼠标操作；
- 完整卡池。
```

### 4. 强调兼容性

每次要求：

```text
现有 CLI 不得破坏；
旧测试必须通过；
旧数据格式需要兼容；
新增字段要有默认值。
```

### 5. 每个阶段必须有证据

不能只以“代码写完”作为完成标准。

至少应包含一项或多项：

- 单元测试；
- CLI；
- 示例输入；
- 示例输出；
- JSON 指标；
- Markdown 报告；
- HTML 可视化；
- 固定回归案例。

## 十一、每一步都要能够直观看到结果

这是本项目后期发现的重要经验。

以后应从项目开始就要求：

```text
每个阶段都要提供一个可直接看到结果的入口。
```

### 数据阶段

输出：

```text
dataset_summary.json
dataset_report.html
```

展示：

- 样本数量；
- 类型分布；
- 异常数据；
- 训练集、验证集、测试集比例。

### 规则阶段

输出：

```text
recommendation_report.html
```

展示：

- 输入状态；
- 候选动作；
- 动作得分；
- 推荐理由；
- 失败原因。

### 模型阶段

输出：

```text
experiment_report.html
```

展示：

- 训练曲线；
- 验证指标；
- 混淆矩阵；
- 分场景效果；
- 模型与规则对比；
- 最佳和最差案例。

### 产品阶段

提供：

- Demo CLI；
- 本地 Web 页面；
- 示例输入；
- 示例输出。

以后可以在每个 Codex 任务末尾加入：

```text
请为本阶段新增一个能直观看到效果的入口，优先使用静态 HTML、Markdown 报告或简单 CLI，不要只输出原始 JSON。
```

## 十二、通用 AI 项目阶段模板

### P0：需求与边界

```text
明确产品目标
明确目标用户
明确不做什么
明确数据来源
明确成功指标
```

### P1：最小业务闭环

```text
输入
→ 核心逻辑
→ 输出
→ CLI/API
→ 测试
```

先不急着训练模型。

### P2：评估闭环

```text
固定测试用例
期望输出
自动指标
失败报告
回归测试
```

### P3：数据闭环

```text
数据生成或采集
校验
清洗
标签
统计
划分
导出
```

### P4：模型闭环

```text
特征
Dataset
模型
训练
验证
保存
加载
推理
```

### P5：模型与基线对比

```text
模型 vs 规则
模型 vs 旧版本
按场景统计
失败案例
误差分析
```

### P6：实验与可视化

```text
固定配置
固定 seed
训练历史
HTML 报告

版本对比
```

### P7：增强算法

```text
更强特征

更合适的损失函数
多步推理
强化学习
```

### P8：产品化

```text
API
Web/桌面/插件
日志
监控
模型版本
用户反馈
```

## 十三、重要技术决策应写入仓库

不要让关键决策只存在聊天记录中。

建议建立：

```text
docs/decisions/
```

每个决策文档包括：

```text
背景
决策
原因
优点
风险
后续影响
```

例如：

```text
0001-use-simulated-data-only.md
0002-use-ranking-model.md
0003-keep-heuristic-baseline.md
```

本项目中的典型决策包括：

- 只做单人招募决策；
- 不依赖真实数据；
- 全部使用模拟数据；
- 先规则推荐，再训练模型；
- 第一版模型蒸馏启发式 Teacher；
- 先用线性模型跑通闭环；
- 训练和在线推理共用同一套特征；
- 每次读取代码先确认最新 Commit。

## 十四、常见错误及改进方式

### 错误 1：一开始就要求完整项目

改进：

```text
先让 GPT 做架构和路线。
```

### 错误 2：直接训练模型

改进：

```text
先完成业务闭环、评估闭环和数据闭环。
```

### 错误 3：Codex 任务过大

改进：

```text
每次只做一个阶段，每阶段只交付一个可验收成果。
```

### 错误 4：只看测试通过

测试通过不代表实际效果好。

改进：

```text
同时看固定案例、指标、失败报告和可视化结果。
```

### 错误 5：不确认最新 Commit

改进：

```text
每次先读取默认分支 HEAD，再 compare 上次 Commit。
```

### 错误 6：规划只存在聊天中

改进：

```text
同步写入 docs/ 和 decisions/。
```

### 错误 7：数据和模型没有版本

改进：

```text
记录数据版本、seed、生成配置、特征版本和模型版本。
```

### 错误 8：模型没有基线对比

改进：

```text
始终保留规则 Baseline，并持续和模型比较。
```

## 十六、推荐的成果目录

每次实验建议生成独立目录：

```text
artifacts/experiments/experiment_name/
├── config.json
├── dataset_summary.json
├── train_metrics.json
├── test_metrics.json
├── compare_metrics.json
├── model.json
├── report.md
└── report.html
```

这样可以做到：

- 不同版本可比较；
- 结果可追溯；
- 配置可复现；
- 模型和数据不会混乱。

## 十七、整套方法的核心原则

可以浓缩为八句话：

```text
GPT 先规划，Codex 再实施。
一次只做一个阶段。
每个阶段必须可验收。
先业务闭环，再模型闭环。
先评估系统，再优化算法。
代码提交后必须重新审查。
重要决策必须写入仓库文档。
每一步都要有可以直观看到的成果。
```

## 十八、最精简的日常使用流程

### 第一次启动项目

```text
向 GPT 说明项目目标、用户、场景、限制和现有仓库。
要求 GPT 先规划，不要直接写代码。
```

### GPT 输出第一阶段任务

```text
复制 GPT 给出的 Codex 提示词。
```

### Codex 完成代码

```text
运行测试并提交代码。
```

### 让 GPT 复查

```text
代码已经更新，请读取最新 Commit，对照上阶段验收标准评估，并规划下一步。
```

### 重复迭代

```text
GPT 规划
→ Codex 实施
→ GPT 复查
→ 用户确认
```

直到项目完成。

---

## 十九、本流程最适合解决的问题

这套流程特别适合：

- 个人长期开发项目；
- AI 助手类项目；
- 数据分析和机器学习项目；
- 自动化工具；
- Web 或小程序 MVP；
- 有现有仓库但架构混乱的项目；
- 需要逐步验证效果的实验性项目；
- 用户不想一次性承担全部工程设计工作的项目。

其最大价值不是“让 AI 写代码”，而是：

```text
让项目始终有明确目标、清晰阶段、可验证结果和可追溯决策。
```
